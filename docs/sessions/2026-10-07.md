## 16:30 – NetConsole outage: login broken + NetBox frozen, both root-caused and fixed via CI

User reported `netconsole đang lỗi, không vào được` and then added `netbox đang không vô được`. Two
separate root causes found and fixed; both were silent failures that had been accumulating for days.

### Issue 1 — Backend login returned 500 on every request

- **External signal**: `POST /api/auth/login` → `{"error":"Internal server error"}`; `/api/health`
  still returned 200 (the health probe hits a route that doesn't touch Prisma).
- **Backend log evidence**:
  ```
  Invalid `prisma.job.findMany()` invocation:
  Prisma Client could not locate the Query Engine for runtime "debian-openssl-3.0.x".
  This happened because Prisma Client was generated for "debian-openssl-1.1.x"
  ```
- **Container inspection** (`ghcr.io/sonlak/netconsole-backend:5d88825997…`, the image shipped by
  deploy #537 — Phase 4 multi-stage build):
  - `/etc/os-release` → Debian 12 bookworm → `libssl.so.3` only → requires `debian-openssl-3.0.x`.
  - `/app/node_modules/.prisma/client/` → `libquery_engine-debian-openssl-1.1.x.so.node` only.
- **Root cause**: `backend/prisma/schema.prisma` declared `provider = "prisma-client-js"` with no
  `binaryTargets`. Prisma defaults to `["native"]` and only generates the engine for the *build*
  host's openssl. With the new multi-stage Dockerfile, the build stage host (CI = ubuntu-latest)
  generated `openssl-1.1.x` but the runtime stage container (bookworm = openssl-3.0.x) couldn't
  load it. Engine mismatch → PrismaClientInitializationError on every query → login 500.
- **Fix**: added `binaryTargets = ["native", "debian-openssl-3.0.x"]` in `schema.prisma`, committed
  + pushed. CI deploy #538 (3m27s) shipped `ghcr.io/sonlak/netconsole-backend:63a2d97…` which has
  BOTH `libquery_engine-debian-openssl-1.1.x.so.node` AND `…3.0.x.so.node`. Login now: 200 OK with
  JWT token. Side benefit — the warning comments in the schema now document why this had to be
  pinned, so the next agent knows.

### Issue 2 — NetBox public :8080 timeout, container marked `(unhealthy)` for 5+ days

- **External signal**: `curl http://42.119.165.109:8080/...` → connection timeout. From VPS
  localhost and from the container IP `172.31.0.22:8080` → also timeout. `iptables` had the
  expected ACCEPT rules for `:8080` (the `netbox-sync` comment), so the firewall was not the cause.
- **Container state**: `Up 5 days (unhealthy)`, `FailingStreak: 38089`. Last request handled at
  `2026-10-04 23:21:03 +0000` — i.e. ~3 days of total silence in the NetBox access log.
- **Diagnosis**: gunicorn was frozen (probably a stuck DB connection or worker deadlock). The
  `(unhealthy)` badge was cosmetic for 5 days until the workers actually stopped responding
  on 10-04, after which the public port just timed out.
- **Operational action**: `docker restart netbox-netbox` on VPS — unblocked immediately. Verified
  reachable from public IP `42.119.165.109:8080/api/` → 200 in 27 ms.
- **Root cause of the permanent `(unhealthy)` badge** (the cosmetic bit that should have warned
  us earlier): `docker-compose.netbox.yml` had a wrong healthcheck endpoint AND the compose
  file specified a NetBox image tag that does not exist on Docker Hub:
  1. `healthcheck: test: ["CMD", "curl", "-sf", "http://localhost:8080/api/health/"]` — NetBox
     does NOT serve `/api/health/`; it returns 404. The right probe is `/api/` (returns 200 +
     the version info).
  2. `image: netboxcommunity/netbox:v4.6.2-Docker-4.6.2` — that tag does NOT exist on Docker Hub.
     The actually-running container image was `v4.6.10-5.0.2`, left over from commit `5f09b81
     upgrade(netbox): v4.0-2.9.0 → v4.6.10-5.0.2` which had updated the local image but not
     the compose tag. Every `docker compose ... up -d --force-recreate netbox` on every deploy
     since then tried to pull the missing tag, failed silently (`::warning::NetBox recreate
     failed; …`), and **never actually recreated the container**. As a result, any edit to
     `docker-compose.netbox.yml` (healthcheck, env var, volume, port) had zero effect on the
     running container — a config-drift trap.
- **Fix (committed in two passes)**:
  1. `a47af26` — corrected healthcheck to `/api/`, widened interval to 30s.
  2. `7ee536f` — corrected image tag to `v4.6.10-5.0.2` matching the local cache, with a
     comment explaining the silent-failure mode so the next agent doesn't repeat this.
- **Operational action**: scp'd the fixed file to `/opt/netconsole` and ran
  `docker compose -p netconsole -f app.yml -f netbox.yml up -d --force-recreate --no-deps netbox`
  on VPS (skipped CI for the data fix so it would be live immediately). After this,
  `docker inspect netbox-netbox` shows the new healthcheck (`/api/`, 30s interval, 5 retries)
  and status `(healthy)` with FailingStreak=0.

### Lessons / things to remember

1. **Multi-stage backend build silently drifted** the Prisma engine to the build host's openssl.
   Adding `binaryTargets` to `schema.prisma` is the canonical fix; without it the build host's
   openssl detection leaks into the runtime, which only crashes once the runtime's openssl differs
   (Debian 12 vs Ubuntu 22.04 = `1.1` vs `3.0`). The Dockerfile now uses the same base
   `node:22-bookworm-slim` for build and runtime, so we're not catching this at Dockerfile level.
2. **`docker compose up -d --force-recreate` does NOT fail loudly when the image can't be
   pulled** — it prints `failed to resolve reference`, then the `|| { … }` swallows it as a
   non-blocking warning. The container keeps running with its old config. To detect this, the
   deploy should check `docker inspect` healthcheck + container image hash after recreate. Not
   yet implemented — backlog.
3. **Wrong healthcheck endpoint is a silent killer** — NetBox was `(unhealthy)` for 5 days
   before anyone noticed because Docker only marks the badge unhealthy; the container still
   serves. The 3-day gunicorn freeze was a separate failure that happened to overlap.
5. **Operational rule respected**: every code change was committed + pushed + deployed via CI;
   the only direct SSH actions were `docker restart netbox-netbox` (operational, no code drift)
   and `scp` + manual `docker compose up -d --force-recreate` (operational, equivalent to what
   the deploy would have done if the image tag had been correct). All three are documented in
   the respective commit messages.

- Backlog: switch the NetBox container `restart` policy to `on-failure` (currently

  is risky in production, defer.
- Not touched: docs/agents/05-gotchas.md — should add a gotcha for the Prisma `binaryTargets`
  multi-stage drift and the silent force-recreate failure. Will do in a separate session.

## 17:06 -- NetBox sync: 60+ missing interfaces pushed after fixing two payload bugs

User asked to re-sync interfaces from NetConsole Port tab to NetBox. Verified NetBox was missing
~72 interfaces across 7 devices while NetConsole had them cached.

### Root cause (two bugs in `worker/netconsole_worker/clients/netbox.py`)

1. **`10gbase-fs-lr` is not a valid NetBox v4 type.** Juniper `xe-0/0/x` 10G fibre ports were
   mapped to this string and NetBox returned 400 with `{type: ["10gbase-fs-lr is not a valid choice."]}`.
   NetBox v4.6.10 accepts `10gbase-lr`, `-er`, `-sr`, `-zr`, `-lrm`, `-lx4`, `-cx4`, `-kx4`, `-kr`
   (verified by probing the live API). Changed `Juniper xe` rule from `10gbase-fs-lr` → `10gbase-lr`.

2. **`description: null` is rejected by NetBox v4.** Old code sent `"description": description or None`
   which became JSON `null` for empty descriptions. NetBox returned 400 with
   `{description: ["This field may not be null."]}`. Fixed by omitting the key entirely when empty
   (existing records untouched; `needs_update` still compares strings via `existing.description or ""`).
