### 12:35 -- Junos self-signed cert + REST HTTPS investigation (NTMK-CORE-QFX5120)

**Câu hỏi của user:** "coi doc juniper thử, tạo cert tự gen được không?" — tạo self-signed
cert để bật `rest https` trên QFX5120.

#### Kết luận quan trọng: Junos 23.4R2 **TỰ SINH** cert được, không cần import

Cú pháp đúng (tìm ra từ error message của Junos, không phải từ doc):

```
set system services web-management https port 8443 system-generated-certificate
```

Junos tự sinh cert self-signed và ghi ra `/var/etc/lighttpd.server.pem` +
`/var/etc/lighttpd.ca.cert`. Verify:
- `subject=CN=AQ40133173, CN=system generated, CN=self-signed`
- `notBefore=Nov 19 04:17:11 2026 GMT` / `notAfter=Nov 18 04:17:11 2031 GMT`
- Kết quả: `*.8443 LISTEN`, TLS 1.3 handshake OK, HTTP 200 (J-Web GUI).

#### Nhưng `rest https` **KHÔNG** dùng được self-generated-certificate

| Lệnh | Kết quả |
| --- | --- |
| `set system services rest https port 8443` | `Missing mandatory statement: 'server-certificate'` |
| `... server-certificate <tên>` | `rest-api: Failed to open certificate file` |
| `... server-certificate system-generated-certificate` | `rest-api: Failed to open certificate file` |
| `... local-certificate <tên>` | `syntax error` (leaf không tồn tại) |
| `... pki-local-certificate <tên>` | `syntax error` |

→ `system-generated-certificate` chỉ hợp lệ dưới `web-management https`, **không** dưới
`rest https`.

#### Tại sao không import được cert tự gen?

Cây `security certificates local <name> certificate <PEM>` **parse được** và **persist
được** trong running config (verify: `show configuration security | display set` hiện
đúng PEM), nhưng `rest https` không đọc được file đó:

- `lighttpd.conf` của rest-api có `server.chroot = "/var/chroot/rest-api"` →
  daemon bị chroot, đọc `/var/etc/*.pem` (nơi Junos đặt cert hệ thống) là **bên ngoài
  jail** → không thấy.
- Thử copy vào `/var/chroot/rest-api/var/tmp/` + trỏ `server-certificate tmp/ncbundle.pem`
  → vẫn `Failed to open certificate file`.
- Thử `server-certificate /var/chroot/rest-api/var/tmp/ncbundle.pem` → `Missing mandatory
  statement: 'server-certificate'` (đường dẫn tuyệt đối không được chấp nhận).

#### Vì sao port 8000 bị DROP (không phải REFUSED)

Đây là phát hiện quan trọng nhất của phiên này:

- `web-api` (PID 22851) và `lighttpd.crypto` đều đang **LISTEN** trên `*.8000` trong
  kernel TCP stack (`show system connections`).
- Nhưng **chính thiết bị cũng không gọi được chính nó**: `file copy
  http://127.0.0.1:8000/restconf/...` → `file-fetch failed`. Cùng lúc đó
  `file copy http://127.0.0.1:8443/` cũng fail (nhưng 8443 trả HTTP 200 qua TLS từ
  worker → chỉ `file copy` của Junos không hỗ trợ HTTPS).
- Junos **không** có `netstat`/`show port-monitor`/`show system internet-management` →
  không có đường nào để xem accept queue.
- Mọi IP của switch đều timeout trên 8000 (kể cả `192.168.61.x` mà SSH cũng timeout).
- Firewall: `show configuration firewall` → **rỗng**. Không có filter nào.
- `set interfaces lo0 unit 250` trong default instance + static route về worker →
  probe cả 22/830/8000 đều TIMEOUT → không phải vấn đề routing-instance.

→ Kết luận: `web-api` daemon của Junos **bị treo/kẹt** (không accept được SYN),
kernel drop SYN do accept queue đầy. Đây là lỗi của Junos runtime, không phải config.
`request system services restart` / `request web-management restart` / `request process
restart web-api` → **tất cả đều không tồn tại** trên Junos EVO (syntax error), và
delete+re-add `rest http port 8000` cũng **không** làm daemon respawn (PID vẫn 22851).

#### Kết luận cuối cho code

- **Đọc Junos**: dùng **NETCONF SSH 830** (đã implement, hoạt động tốt — GET_SYSTEM
  0.58s, ARP/MAC/LLDP/CHASSIS đều OK, serial `AQ40133173` lấy được).
- **Ghi Junos**: dùng **NETCONF SSH 830** `<load-configuration format="text" action="set">`
  + `<commit-configuration/>` (đã implement, hoạt động).
- **RESTCONF/REST API trên QFX5120 này: KHÔNG dùng được.** Port 8000 luôn drop SYN
  (kể cả từ chính thiết bị). Không nên đầu tư thêm vào hướng REST.
- `rest https` + self-signed cert: cần `server-certificate` trỏ tới file Junos đọc được
  → không làm được với cert tự gen (chroot của rest-api).

#### ⚠️ Sự cố đã gây ra và đã khôi phục

Trong lúc dọn dẹp, tao chạy `<load-configuration format="xml" action="replace">` với
`<configuration><security/></configuration>` để xóa cert test — **Junos hiểu đây là
replace TOÀN BỘ config**, và `<security/>` rỗng khiến running config bị **xoá sạch
(0 bytes)**.

- Phát hiện qua: `show configuration` → `(empty)`, `show system connections` mất hết
  interface.
- `rollback 0..5` → **không giúp** (snapshot `juniper.conf.*.gz` chỉ ~3.6 KB vì Junos
  đã compact config).
- **Cứu bằng cách khác**: `10.1.240.250` (vme.0) chết vì mất static route
  `192.168.81.0/24` trong `mgmt_junos` → không có đường về worker subnet → không trả
  SYN-ACK. Nhưng `10.1.240.254` (irb.240) **vẫn sống** → dùng nó để vào NETCONF
  (830) và load lại route.
- Kết quả: `10.1.240.250:22/830 → OPEN`, config đầy đủ **165.278 bytes** (khớp 100%
  với trạng thái ban đầu), tất cả task đọc Junos smoke-test PASS, serial OK.

**Bài học (bắt buộc nhớ):**
1. **KHÔNG BAO GIỜ** dùng `load-configuration action="replace"` với một subtree rỗng
   để "dọn dẹp" — phải dùng `delete <path>` có chỉ định rõ ràng.
2. Luôn có **backup config** trước khi thay đổi: `show configuration | save /tmp/x.conf`
   (Junos `file copy`), hoặc `show configuration | display set` ra file ngoài.
3. Trước khi xóa bất kỳ route/interface nào, **luôn kiểm tra đường đi ngược** — nếu
   xóa route quản lý mà chỉ còn một đường vào duy nhất qua chính route đó thì mất
   quyền truy cập.
4. `rollback 0` trên Junos **không** phải "config trước commit cuối" một cách an toàn —
   nó không khôi phục được config bị replace toàn bộ.
