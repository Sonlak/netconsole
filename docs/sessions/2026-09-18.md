# 2026-09-18

## 09:30 — fix(backend): terminal SSH sync-throw crash + session caps

**Symptom:** Live web at https://42.119.165.109:8443 returned
`POST /api/auth/login → 502 Bad Gateway` for ~1 minute starting at 02:26:35
UTC (09:26 ICT). nginx error log: `connect() failed (111: Connection
refused) while connecting to upstream, client: 103.63.105.206,
upstream: "http://172.31.0.3:3000/api/auth/login"`. After 02:27:28
nginx started getting 200s again — but the backend then crashed a SECOND
time at 02:29:44 (UTC), same cause. User impact: anyone hitting the site
in those two windows couldn't log in.

**Root cause:** `backend/src/websocket/terminal.ts::tryOpenShell` called
`ssh.shell(options, callback)` from ssh2 without a try-catch. When the
SSH server (10.10.20.101) accepted the TCP+SSH handshake then closed the
socket before the shell channel opened, ssh2 threw `Error: Not connected`
**synchronously** from inside `Client.shell()`. The throw bypassed the
callback entirely, propagated up the event-loop as an uncaughtException,
and Node.js exited with code 1. Docker's `restart: unless-stopped`
restarted the backend — but the same user opened another terminal to the
same device and it crashed again 3 minutes later.

Stack trace (from `/var/lib/docker/containers/...-json.log`):
```
/app/node_modules/ssh2/lib/client.js:1251
      throw new Error('Not connected');
Error: Not connected
    at Client.shell (.../ssh2/lib/client.js:1251:13)
    at tryOpenShell (file:///app/dist/websocket/terminal.js:187:33)
```
Confirmed on the SECOND crash. The first crash's logs are gone (rotated
by docker), but the journalctl message `restarting container ... exitCode=1`
matches the same pattern (manualRestart=false, restartCount=1 → 2).

This is a known ssh2 behaviour — when the underlying transport is torn
down mid-handshake, `Client.shell()` and `Client.connect()` can throw
sync from inside their own implementation, not through the callback. The
library never documented this and there's no GitHub issue that fully
explains it; the workaround is to wrap the call.

**Fix:**
- `backend/src/websocket/terminal.ts` — three changes:
  1. Wrap `ssh.shell(...)` in try-catch (the actual bug).
  2. Wrap `ssh.connect(...)` in try-catch (defensive, same root cause).
  3. Add `shellOpenTimer` (default 15s, `SHELL_OPEN_TIMEOUT_MS` env) that
     ends the session if the shell callback never fires.
- `backend/src/websocket/terminal.ts` — capacity guards (prevents the
  NEXT class of incident):
  - `MAX_TERMINALS_PER_USER` (default 5, env-overridable): per-user cap
    on active SSH terminals. Tracks in module-level `Map<userId, count>`.
  - `MAX_TERMINALS_GLOBAL` (default 30): backend-container-wide cap.
  - Slot acquired at `connect` time, released on `cleanup()` (guarded
    with `_released` flag so disconnect/cleanup can't double-release).
- `backend/src/websocket/terminal.ts` — last-resort safety net:
  `process.on('uncaughtException')` and `process.on('unhandledRejection')`
  handlers that log + survive instead of dying. (Belt + suspenders —
  per-call try-catches should catch ssh2's quirks, but this prevents
  future unknown library throws from taking the API down.)
- `docker-compose.app.yml` — `backend` service: `mem_limit: 1g`,
  `mem_reservation: 512m`, `cpus: '1.5'`. Measured peak was 229MiB
  (during ARP collect); 1GiB is generous headroom. Cap prevents one
  runaway admin / memory leak from starving Postgres / Kea / worker
  on the same VPS.

**Why not scale the worker instead?** The worker is fine — it has
`SSHConnectionPool` (single-conn-per-host, 600s idle reaper, 60s
keepalive) and only handles queued one-shot jobs (LLDP/CDP/ARP/config
collects). The bottleneck is the **backend**, which holds long-lived
SSH sockets for every interactive terminal WebSocket. Adding more
workers doesn't help because terminals are WS-typed to the backend
container. Adding CPU/RAM to backend doesn't help either — the fix
is caps + better error handling, not more resources. (If the global
cap of 30 turns out to be too low for real ops, raise it via
`MAX_TERMINALS_GLOBAL` env var without a redeploy.)
