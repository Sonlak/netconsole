# 2026-09-18

## 09:30 — fix(backend): terminal SSH sync-throw crash + session caps

**Symptom:** Live web at https://42.119.165.109:8443 returned
`POST /api/auth/login → 502 Bad Gateway` for ~1 minute starting at 02:26:35
UTC (09:26 ICT). nginx error log: `connect() failed (111: Connection
refused) while connecting to upstream, client: 103.63.105.206,
upstream: "http://172.31.0.3:3000/api/auth/login"`. After 02:27:28
nginx started getting 200s again — but the backend then crashed a SECOND
time at 02:29:44 (UTC), same cause. User impact: anyone hitting the site
in those two windows couldn't log in.

**Root cause:** `backend/src/websocket/terminal.ts::tryOpenShell` called
`ssh.shell(options, callback)` from ssh2 without a try-catch. When the
SSH server (10.10.20.101) accepted the TCP+SSH handshake then closed the
socket before the shell channel opened, ssh2 threw `Error: Not connected`
**synchronously** from inside `Client.shell()`. The throw bypassed the
callback entirely, propagated up the event-loop as an uncaughtException,
and Node.js exited with code 1. Docker's `restart: unless-stopped`
restarted the backend — but the same user opened another terminal to the
same device and it crashed again 3 minutes later.

Stack trace (from `/var/lib/docker/containers/...-json.log`):
```
/app/node_modules/ssh2/lib/client.js:1251
      throw new Error('Not connected');
Error: Not connected
    at Client.shell (.../ssh2/lib/client.js:1251:13)
    at tryOpenShell (file:///app/dist/websocket/terminal.js:187:33)
```
Confirmed on the SECOND crash. The first crash's logs are gone (rotated
by docker), but the journalctl message `restarting container ... exitCode=1`
matches the same pattern (manualRestart=false, restartCount=1 → 2).

This is a known ssh2 behaviour — when the underlying transport is torn
down mid-handshake, `Client.shell()` and `Client.connect()` can throw
sync from inside their own implementation, not through the callback. The
library never documented this and there's no GitHub issue that fully
explains it; the workaround is to wrap the call.

**Fix:**
- `backend/src/websocket/terminal.ts` — three changes:
  1. Wrap `ssh.shell(...)` in try-catch (the actual bug).
  2. Wrap `ssh.connect(...)` in try-catch (defensive, same root cause).
  3. Add `shellOpenTimer` (default 15s, `SHELL_OPEN_TIMEOUT_MS` env) that
     ends the session if the shell callback never fires.
- `backend/src/websocket/terminal.ts` — capacity guards (prevents the
  NEXT class of incident):
  - `MAX_TERMINALS_PER_USER` (default 5, env-overridable): per-user cap
    on active SSH terminals. Tracks in module-level `Map<userId, count>`.
  - `MAX_TERMINALS_GLOBAL` (default 30): backend-container-wide cap.
  - Slot acquired at `connect` time, released on `cleanup()` (guarded
    with `_released` flag so disconnect/cleanup can't double-release).
- `backend/src/websocket/terminal.ts` — last-resort safety net:
  `process.on('uncaughtException')` and `process.on('unhandledRejection')`
  handlers that log + survive instead of dying. (Belt + suspenders —
  per-call try-catches should catch ssh2's quirks, but this prevents
  future unknown library throws from taking the API down.)
- `docker-compose.app.yml` — `backend` service: `mem_limit: 1g`,
  `mem_reservation: 512m`, `cpus: '1.5'`. Measured peak was 229MiB
  (during ARP collect); 1GiB is generous headroom. Cap prevents one
  runaway admin / memory leak from starving Postgres / Kea / worker
  on the same VPS.

**Why not scale the worker instead?** The worker is fine — it has
`SSHConnectionPool` (single-conn-per-host, 600s idle reaper, 60s
keepalive) and only handles queued one-shot jobs (LLDP/CDP/ARP/config
collects). The bottleneck is the **backend**, which holds long-lived
SSH sockets for every interactive terminal WebSocket. Adding more
workers doesn't help because terminals are WS-typed to the backend
container. Adding CPU/RAM to backend doesn't help either — the fix
is caps + better error handling, not more resources. (If the global
cap of 30 turns out to be too low for real ops, raise it via
`MAX_TERMINALS_GLOBAL` env var without a redeploy.)

**Deployed:** commit TBD via GitHub Actions → backend container. The
existing CI/CD pipeline handles rollback automatically if any step
fails (rollback.yml verified working 2026-09-16).

**What's left:**
- Move interactive terminals from backend to a dedicated container if
  global cap becomes a real limit (out of scope — would need sticky
  WS routing, plus an SSH-to-worker tunnel, bigger refactor).
- Investigate why 10.10.20.101 dropped SSH right after the banner
  (could be lab device config, not the platform's fault).

## 10:05 — fix(worker/junos): pool + retry for read RPCs (MAC/ARP/interfaces/VLAN/config/log)

**Symptom:** Auto-collect (every 30 min) sometimes returns 0 entries for MAC
and ARP on Junos devices even though `ping` reports the device as online.
User observation: "collect MAC, ARP, interface của Junos lúc được lúc không".
Examples from live backend log (after the 09:30 deploy):

```
[mac] 10.10.20.221 collected via REST in 1627ms (0 entries)
[arp] 10.10.20.221 collected via REST in 2084ms (0 entries)
[ping] checked=8 online=5 offline=3 skipped=0
```

Device is reachable but RPC returns no data — same device, same lab, picked
up on the next sweep without issue.

**Root cause:** `worker/netconsole_worker/junos_rest.py::_fetch_with_retry`
was defined at line 272 but **never called**. The MAC/ARP/interface/VLAN/
config/log read helpers (`fetch_ethernet_switching_table`,
`fetch_arp_table`, `fetch_interface_information`, `fetch_vlan_information`,
`fetch_interfaces_set_config`, `fetch_interface_configuration`,
`fetch_configuration`, `fetch_log_information`) all called `fetch_junos_rpc`
directly. That helper, when invoked without a pooled `client` arg, opens
a one-shot `httpx.Client` per call (full TCP+TLS+Basic-auth handshake
every time), with NO retry on transient errors.

So when the lab bridge spikes 5-20 s (already documented as gotcha #15:
cRPD RESTCONF cold-start), a single one-shot `httpx.Client` times out
mid-request → empty payload → parser yields `entries: []` → user sees
"0 entries" → looks like "lúc được lúc không".

**Fix:** Wire the read helpers into the existing `JunosRESTPool` +
`_fetch_with_retry` infrastructure (both already existed; the pool was
only used by `apply_set_configuration` and `probe_device_identity`).

- `_fetch_with_retry` rewritten to accept `**kwargs` so it can forward
  `body=`, `params=`, `accept=` etc. to `fetch_junos_rpc` — needed for
  POST-style RPCs like `<get-configuration>` (used by `fetch_configuration`,
  `fetch_interface_configuration`, `fetch_interfaces_set_config`). All
  previous args remain backwards compatible (`username`, `password`,
  `scheme`, `port`, `verify_tls`, `timeout` are now optional since the
  pooled `client` carries auth context).
- `fetch_ethernet_switching_table`, `fetch_arp_table`,
  `fetch_interface_information`, `fetch_vlan_information`,
  `fetch_configuration`, `fetch_log_information`,
  `fetch_interface_configuration`, `fetch_interfaces_set_config` now
  borrow from `JunosRESTPool` and call `_fetch_with_retry(client=...)`.

Effect on a single sweep: TCP+TLS+Basic-auth handshake runs once per
device per `JunosRESTPool` reaper cycle (10 min idle) instead of once
per RPC. Transient 5-20 s spikes now retry up to 3 attempts (1 s, 2 s
backoff) on the same pooled socket — no full re-handshake on retry.

Write path (`apply_set_configuration`, `rollback_configuration`) and
managed-check probe (`probe_device_identity`) are unchanged; they were
already using the pool.

**Deployed:** commit TBD via GitHub Actions → worker container (worker
image rebuild + container restart). Backend stays up.

**What's left:**
- Watch `[mac]/[arp]` collector logs over the next few sweeps. If "0
  entries" persists for a specific device, the issue is on the device
  side (cRPD RESTCONF daemon wedged) — restart `netconf-yang` on the
  affected Junos. Not a NetConsole bug.
- The two `fetch_junos_rpc("get-system-uptime-information")` calls in
  `juniper.py::probe_identity` still use one-shot clients. Lower priority
  (called only every 30 min on managed check) — can be migrated in a
  follow-up if uptime becomes flaky too.
