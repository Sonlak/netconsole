## 13:09 ΓÇö fix(frontend): cross-tab refresh coordination (no more multi-tab logout)

**User: "User bß╗ï logout bß║Ñt ngß╗¥ giß╗»a chß╗½ng khi mß╗ƒ nhiß╗üu tab ΓÇö fix UX multi-tab replay."**

### Root cause (confirmed by audit)

The backend refresh-token flow has strict replay protection (see
backend/src/lib/refreshTokens.ts:84-91): every successful
/api/auth/refresh call CONSUMES the old refresh row and rotates a new
pair. Two tabs of the same user opening the dashboard simultaneously and
both hitting a 401 within the same access-token window (15 min) would:

1. Tab A POSTs /refresh -> backend consumes row, issues new pair
2. Tab B POSTs /refresh -> backend sees consumedAt -> fires
   replay_detected -> **revokes the entire refresh chain for that user**
3. Every tab of that user has to log back in

The per-tab single-flight in http.ts only prevented concurrent POSTs
within one tab. Cross-tab coordination was missing.

### Fix: BroadcastChannel + localStorage leader claim

New module frontend/src/lib/refreshCoordinator.ts (~390 lines):

- One leader tab per browser. Other tabs wait for the leader to broadcast
  the new (access, refresh) pair via BroadcastChannel and copy it locally.
- Leader election: candidate writes a claim (requestId, startedAt) to
  localStorage[LEADER_KEY], waits 80 ms, re-reads. If our requestId
  survived, we are the leader. Last-write-wins resolves simultaneous
  claims deterministically.
- Leader heartbeat: startedAt refreshed every 3 s while /refresh is in
  flight, so a slow backend does not cause premature takeover. 8 s claim
  TTL means a crashed leader tab's claim expires and another tab can claim.
- Follower timeout: 20 s - if the leader never broadcasts (hung backend),
  follower clears local auth and lands on /login.
- Graceful fallback: if BroadcastChannel / localStorage unavailable,
  coordinator just calls refreshTokens() directly (per-tab single-flight
  in http.ts still works).

### Files changed

- frontend/src/lib/refreshCoordinator.ts - NEW, leader election + broadcast
  plumbing (coordinatedRefresh(), broadcastLogout(), broadcastAuthCleared()).
- frontend/src/api/http.ts - doRefresh() now calls coordinatedRefresh()
  instead of refreshTokens(). Both 401-handling blocks (in handleResponse
  and authJsonFetch) push broadcastAuthCleared() so any tab that has not
  yet entered the follower queue also drops its local session, instead of
  wasting a POST on the now-revoked chain.
- frontend/src/api/auth.ts - logout() now calls broadcastLogout() after
  clearing local auth, so other tabs drop their session too.

### Build verification

npm run build (which runs tsc -b && vite build) passes - TypeScript
strict mode compiles clean, no warnings related to the changes
(pre-existing 500 kB chunk warning is unrelated).

### Behaviour summary

| Scenario                          | Before                              | After                                                |
|-----------------------------------|-------------------------------------|------------------------------------------------------|
| 1 tab, access expires             | 1 POST /refresh, success            | Same (1 POST, success)                               |
| 2 tabs, sequential 401s           | Both POST, 2nd triggers replay      | Only leader POSTs, follower waits for broadcast      |
| 2 tabs, simultaneous 401s         | Both POST, replay, force logout     | Leader election via 80 ms claim window, at most 1 POST |
| Tab crashes mid-refresh           | Refresh fails, user logs back in    | Claim expires 8 s, another tab retries, no user-visible change |
| Logout in tab A                   | Tab B keeps using dead refresh      | Tab B receives broadcastLogout, clears immediately    |
| Replay detected                   | Tab A clears, tabs B/C waste POSTs  | All tabs receive broadcastAuthCleared, drop immediately |
| Old browser (no BroadcastChannel) | Worked (with replay risk)           | Per-tab single-flight only, same as before, no regression |
