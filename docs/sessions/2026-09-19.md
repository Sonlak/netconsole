### Issue 2 — F6-CORE-01 MAC table empty (user's specific complaint)

Probe revealed the actual device config:
- LAB-F6-CORE-01: all interfaces `family inet address` (pure L3 router,
  no `family ethernet-switching`, no `vlans`). The `get-ethernet-switching-table-information`
  RPC returns `<l2ng-l2ald-rtb-macdb></l2ng-l2ald-rtb-macdb>` — literally
  empty envelope. MAC learning only happens on L2 interfaces, so this is
  **correct device behaviour**, not a bug.

Two sub-issues found:

**A. Backend MAC fast-path parser was broken**: `parseMacTableXml` looked for
`ethernet-switching-table-information` as the parent block — but the actual
RPC response root is `<l2ng-l2ald-rtb-macdb>` (modern Junos 20+ format). Fixed
the parser to walk the XML tree recursively and find `<l2ng-mac-entry>`
blocks directly (same approach as the worker parser in
`worker/netconsole_worker/parsers/mac_table_rpc.py::_walk_xml`).

**B. No L3-only distinction**: Backend returned 0 entries with the same
generic message as "L2 device with no learned MACs yet". Fixed:
- Added `l3Only` detection by checking if the raw XML is an empty
  `<l2ng-l2ald-rtb-macdb></l2ng-l2ald-rtb-macdb>` envelope.
- Result carries `l3Only: true` and a descriptive message.
- Frontend renders an `<Alert type=info>` explaining that MAC learning
  only happens on L2 interfaces, so an L3-only device has an empty
  MAC table by design.

**Issue (user-reported 2026-09-19 11:40 ICT):**
- LAB-F3-AS-02 (10.10.20.212, Cisco IOS-XE 17.16.1a Virtual XE Software) terminal
  failed with `Handshake failed: no matching C->S MAC`. Backend logs showed
  two failed attempts: `Session f659173b...: SSH error: Handshake failed:
  no matching C->S MAC`.

**Root cause:** ssh2's default algorithm list omits the
`*-etm@openssh.com` MAC variants (`hmac-sha2-512-etm@openssh.com`,
`hmac-sha2-256-etm@openssh.com`) that Cisco IOS-XE 17.x advertises as
its preferred C->S MAC. Confirmed via paramiko probe on 2026-09-19
against the same device — paramiko selected `hmac-sha2-256-etm@openssh.com`
by default, while ssh2 had no overlap.

Server's full KEXINIT offer (verified):
- KEX: curve25519-sha256@libssh.org, ecdh-sha2-nistp256/384/521,
  diffie-hellman-group16-sha512, diffie-hellman-group-exchange-sha256,
  diffie-hellman-group14-sha256
- MAC: hmac-sha2-256, hmac-sha2-512, hmac-sha2-256-etm@openssh.com,
  hmac-sha2-512-etm@openssh.com, hmac-sha1, hmac-md5, hmac-sha1-96,
  hmac-md5-96
- Cipher: aes{128,192,256}-ctr, aes{128,192,256}-cbc, 3des-cbc,
  aes128-gcm@openssh.com, aes256-gcm@openssh.com
- HostKey: ssh-ed25519, ecdsa-sha2-nistp*, rsa-sha2-{256,512}

ssh2 only had the non-ETM MACs + non-GCM ciphers — no match.

**Fix:** add `hmac-sha2-512-etm@openssh.com`, `hmac-sha2-256-etm@openssh.com`,
`hmac-sha1-etm@openssh.com`, `hmac-md5-96` to the `algorithms.hmac` list,
and `aes128-gcm@openssh.com`, `aes256-gcm@openssh.com` to `algorithms.cipher`.
ETM variants listed first so they're the KEXINIT preference (no extra
round-trip). Existing non-ETM algos still listed for older IOS peers.

**Files:**
- `backend/src/websocket/terminal.ts` — extend the existing algorithms block

**Worker (paramiko) unaffected** — paramiko's default algorithm list
already includes the ETM variants, which is why the same device's
ARP/MAC collect via `iosxe.py::get_arp` SSH fallback works fine.
This bug was ssh2-only (terminal + the backend's `labSsh.ts` discovery
