# NetConsole — Daily Session Log — 2026-10-19

## 09:00 — Deploy #639: disk-pressure incident + recovery

User reported "commit push keeps failing". Investigation found the site
was DOWN since deploy #639 at 02:31Z failed AND auto-rollback #286
also failed. VPS root disk was 100% full (114M available out of 70G).

### Root cause

`/var/lib/containerd` accumulated **61G** of unused overlay layers
+ 15G of orphaned blobs over ~10 deploys. Every deploy pulls a new
SHA tag and never removes the old ones (each backend image is ~916MB,
worker ~284MB, frontend ~87MB; 10 deploys × ~1.3GB ≈ 13G new content
plus pulled layers stacking on top).

When disk hit 100%, `docker compose up -d` returned:
```
failed to create temp dir:
mkdir /var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/
    snapshots/new-2887045774: no space left on device
```

The deploy job's step 7 ("Build & restart") logged `::warning::` but
continued with `--remove-orphans`, so the containers ended up "Created"
without ever being "Started". Step 8 ("Wait for backend healthy")
correctly failed after 90s of `curl http://172.31.0.3:3000/api/health`
returning nothing.

Auto-rollback then fired (workflow_run trigger) but:
- `.last-deploy-rollback` and `.rollback-before-deploy-sha` markers
  were MISSING on VPS (rsync partial-transfer in some previous deploy
  must have wiped them).
- Rollback fell back to git HEAD = current broken SHA `14465764`.
- Pulled the same broken 1446576 image, same disk-full failure.
- 3-tier fallback (`up --build` → `up` → `restart`) all failed.
- Site stayed DOWN.

### Fix (applied)

1. **Manual recovery via SSH** (allowed per deploy rule §"If CI is broken"):
   - `docker container prune -f` → reclaimed 0B (none stopped).
   - `docker image prune -a -f` → reclaimed ~20G (all old SHA tags).
   - `docker compose up -d --force-recreate backend worker frontend redis`.
   - All 7 containers now Up + healthy. Site back online.
   - `/api/health` returns OK with `version:"main" gitCommit:"14465764"`.

2. **Restored missing `.last-deploy-sha` / `.rollback-before-deploy-sha`**
   markers (written via `cat <<EOF` to avoid CRLF corruption via scp).
   Both point at `14465764` (the SHA that's now actually running).

3. **`deploy.yml` — added disk-pressure guard** at start of
   "Build & restart app services" step:
   - Logs `df -h /` so future failures are diagnosable.
   - If available space < 5G, runs `docker container/image/volume
     prune -f` before pulling new images.
   - All prune lines use `|| true` so a prune error never blocks the
     deploy — the `up` step surfaces the real problem.

4. **`rollback.yml` — updated FALLBACK_SHA**: `8dab6659…` → `2113812…`.
   `2113812` ("fix(frontend): revert USER nginx + pid directive") is
   the last commit confirmed running on the VPS BEFORE the
   disk-pressure incident. The backend image for `14465764` is
   byte-identical to `2113812`'s (the backend Dockerfile hasn't
   changed since), so `2113812` is a safe default if markers are ever
   wiped again.

### What was NOT the cause

- NOT a code regression — the deployed 1446576 backend image is the
  same as 2113812 backend image (Docker build cache reused same layers).
- NOT a compose-file bug — the security fixes (jwt fail-fast,
  HttpOnly cookie, RBAC) all worked.
- NOT a docker-compose failure — once disk was freed, `up -d` succeeded.

### Lessons / follow-up

- **Cleanup is missing for production overlay images**. Should add
  periodic `docker image prune` to a separate workflow (`cron: weekly`)
  or to rollback.yml too. For now the deploy guard handles it on next
  push.
- **Markers being silently wiped is bad**. The deploy guard's
  "Save rollback marker" step is idempotent (won't overwrite an
  existing marker), but if markers are wiped AND a deploy fails,
  rollback falls back to current git HEAD = the failing SHA = no
  recovery. FALLBACK_SHA is the only safety net. Maybe backstop
  markers into git as well? Or write to `/etc/netconsole.fallback_sha`?
  Backlog.
- **Deploy job should fail-fast when disk is full**, not after 90s
  of waiting for backend to come up. The new guard prevents the
  recurrence.
