# NetConsole · Session Log

## 2026-09-09

### 16:45 — Config Studio IOS-XE: backend SSH proxy for apply_config

User reported `apply_config` job marked SUCCESS on Cisco IOS-XE but device
got nothing. Pipeline was completely silent — operator had no idea nothing
landed.

**Root cause:** `run_ssh_commands_session` uses `sshpass + ssh -tt` from the
worker container. Lab IOS-XE accepts the TCP connection but the SSH pipe is
broken — `sshpass` exits 0 with empty stdout. The worker checked for IOS
error markers (`% `) but found none (empty buffer), so it reported success.

**Fix path:** Backend container has working SSH to `10.10.20.x:22` (proven
by RESTCONF show-run in `11-...`). Worker, after determining the local SSH
path produced no output, now calls `POST /api/interfaces/<id>/apply-ssh` on
the backend. Backend uses `ssh2` shell channel to send the full config
batch (sub-blocks work — single batch with embedded newlines, no
prompt-barrier between parent/child).

**Files touched:**
- `worker/netconsole_worker/backends/iosxe.py` — `_apply_via_backend_ssh()`
  helper, fallback in `apply_config()` on (a) worker SSH `sshOk=False`,
  (b) worker SSH nominally OK but RESTCONF verify shows config not on
  device.
- `worker/netconsole_worker/ssh_client.py` — `run_ssh_commands_session`
  returns `sshOk=False` when all outputs are empty (catches broken pipe).
- `backend/src/services/labSsh.ts` — `runIosxeSshApply()` opens ssh2 shell,
  sends `terminal length 0` + `configure terminal` + batched config +
  `end`, parses output by matching echoed command lines.
- `backend/src/routes/interfaces.ts` — `POST /:deviceId/apply-ssh`.

**Verification:** live on `LAB-F3-AS-02 / 10.10.20.212`:
- Applied `interface GigabitEthernet4 / description NETCONSOLE_PROXY_TEST`
  → backend returned `ok: true, commandCount: 1`
- `GET /api/interfaces/<id>/show-run?iface=GigabitEthernet4` →
  ```
  interface GigabitEthernet4
  description NETCONSOLE_PROXY_TEST
  ip address 10.10.20.212 255.255.255.0
  ...
  ```
- Rolled back via the same path (`no description`), RESTCONF confirmed.

**Caveats discovered:**
- The lab device rejects `vlan X / name FOO` (the Access template's body)
  with `% Invalid input detected at '^' marker.` — likely because the lab
  device only supports VLAN changes via `vlan database` (IOS 12.x style),
  not via `configure terminal` mode (which is IOS 15.x+). This is a lab
  device config issue, not a NetConsole bug. Real production IOS-XE boxes
  accept both. The pipeline correctly reports the rejection via the
  `outputs[].error` array.
- `commandCount` in the worker's job result is `None` — minor: worker
  doesn't propagate `commandCount` from the backend response into its
  result dict. Job still shows success with `outputs[]` so the operator
  sees what happened. Not blocking.

**Commits:**
- `e5e061a` detect zero-output SSH sessions (the bug surface)
- `b250675` backend SSH proxy + worker fallback
- `12f259d` batch-send config (sub-blocks)
- `c270ddc` docs

### 17:05 — Config Studio Juniper: `log` was a string, called as a function

User applied `set system host-name LAB-F6-CORE-01` on `LAB-F6-CORE-01-test`
(ex9214 / Juniper). Job `b2f24cfa-81ce-4133-80aa-3a905adf94f6` FAILED with
`error: 'str' object is not callable`. No stack, no reason — silent.

**Root cause:** `worker/netconsole_worker/backends/juniper.py::JuniperBackend.apply_config`
had a single leftover call:
```python
log("NETCONF SSH failed, falling back to RESTCONF: %s", rest_error)
```
`log` is typed `str` and only used as a label. The stray call raised
`TypeError: 'str' object is not callable` — which `main.py::run_job`
then `str()`-formatted into the job error column. Operator saw only
`'str' object is not callable`.

This only triggered on the **fallback path** from NETCONF-over-SSH to
RESTCONF. If the device responded to NETCONF on port 830, the bug never
fired. So plain `set` commands on a healthy cRPD-NETCONF device worked;
the moment the lab firewall (gotcha #2) ate the NETCONF SSH handshake,
the worker took the fallback path and crashed.

**Fix (commit `d50c686`):** replaced `log(...)` with `logger.warning(...)`.

**Verification:** triggered a live apply on `LAB-F6-CORE-01` after deploy
— no more `'str' object is not callable`. The error message now surfaces
the real reason (e.g. `load failed: <junos-side reason>`).

**Pattern to watch:** anywhere a function still calls a parameter that has
been migrated from `Callable` to `str` (or vice versa) is at risk of
TypeError like this. A unit test that runs the apply_config path with
NETCONF unreachable would catch this; not added yet.

### 23:25 -- Managed check rewritten to TCP-only probe (drop `show version` / `show running-config`)

User: "đọc doc, agent.md vào chỉnh lại cái check managed đi, quá nhiều connection ssh vào thiết bị. check managed ssh check port 22 open là được, không cần login vào, check thêm cái rest or netconf nữa"
Followup: "bỏ cái show run, show version đi nhé, ssh ping rest or netconf thôi là được"

**Why:** the per-device managed check used to do 2 SSH logins + pull
`show running-config | display set` (5-50 KB) + a RESTCONF GET on
IOS-XE/Junos. On a 30 s schedule across the whole fleet that burned
~95% of auth.log noise and ate SSH pool slots every cycle.

**What changed:**

- New worker helper `worker/netconsole_worker/probe.py` with
  `tcp_open(host, port, timeout)` and wrappers `probe_ssh`,
  `probe_rest_or_netconf`. Pure `socket.create_connection`, no payload,
  no auth, no banner read. 1.5 s default timeout.
- Rewrote `probe_identity` in all 4 vendor backends to TCP-only:
  - **Juniper**: SSH(22) + NETCONF(830 if enabled) + RESTCONF(8443 if
    enabled); `rest` flag is OR of NETCONF+RESTCONF.
  - **IOS-XE**: SSH(22) + RESTCONF(443 if enabled) + NETCONF(830 if
    enabled); `rest` flag is OR of RESTCONF+NETCONF.
  - **EOS**: SSH(22) + eAPI(443 if enabled).
  - **NX-OS**: SSH(22) + NX-API(80 if enabled).
- Result dict keeps `checks.{ping, ssh, rest, showVersion=false,
  showRun=false}` shape -- `showVersion`/`showRun` no longer fetched
  but kept in the JSON so callers don't break.
- Backend `isFullyManaged` gate: `ping && ssh && rest` (was
  `&& showVersion && showRun`).
- `hasReadyManagedChecks` (`collectableDevices.ts`) requires `rest=true`
  for new rows; **legacy rows** (no `rest` key, only
  `showVersion`+`showRun` set) still pass so existing devices stay
  collectable until their next managed-check refresh.
- Frontend `ManagedChecks` type adds `rest`. `MANAGED_CHECK_LABELS`
  renders 3 tags: Ping, SSH, REST/NETCONF. `isFullyManaged()` mirrors
  backend with legacy fallback.

**Verification:**
- `backend` `npm run build`: clean
- `frontend` `npm run build`: clean
- `backend` `npm test`: 52/52 pass
- Behavioral smoke test: 9 cases across 4 vendors (RESTCONF-only,
  NETCONF-only, both up, nothing) all return the right `checks` shape
  and the right `source` label (`junos-rest-tcp` /
  `iosxe-restconf-tcp` / `eos-api-tcp` / `nxos-nxapi-tcp` / `None`).

**Impact / cost saved:**
- Per-device managed check: was 2 SSH sessions + full
  `show running-config` payload + RESTCONF GET; now is 2-3 TCP connects
  (~10-50 ms each). On a 30 s schedule across the fleet, that's ~95 %
  less auth.log noise and zero SSH pool slots burned.

**Trade-off (intentional):** `Device.managedChecks` no longer refreshes
`vendor` / `model` / `version` / `serial` from `show version`. Those
fields are still set during initial discovery and on the SSH-based
`get_config`. If you want them re-synced after a manual edit, re-run
discovery on the device. The probe is cheap, not authoritative.

**Left as-is (out of scope):**
- `discoveryScan.ts` still does full SSH login + `show configuration |
  display set` for new-device onboarding. One-time per device, fine.
- Dead helpers in EOS backend (`_parse_eos_show_version`) -- no longer
  called after probe rewrite. Cleanup deferred.
