## 2026-09-09

### 16:45 — Config Studio IOS-XE: backend SSH proxy for apply_config

User reported `apply_config` job marked SUCCESS on Cisco IOS-XE but device
got nothing. Pipeline was completely silent — operator had no idea nothing
landed.

**Root cause:** `run_ssh_commands_session` uses `sshpass + ssh -tt` from the
worker container. Lab IOS-XE accepts the TCP connection but the SSH pipe is
broken — `sshpass` exits 0 with empty stdout. The worker checked for IOS
error markers (`% `) but found none (empty buffer), so it reported success.

**Fix path:** Backend container has working SSH to `10.10.20.x:22` (proven
by RESTCONF show-run in `11-...`). Worker, after determining the local SSH
path produced no output, now calls `POST /api/interfaces/<id>/apply-ssh` on
the backend. Backend uses `ssh2` shell channel to send the full config
batch (sub-blocks work — single batch with embedded newlines, no
prompt-barrier between parent/child).

**Files touched:**
- `worker/netconsole_worker/backends/iosxe.py` — `_apply_via_backend_ssh()`
  helper, fallback in `apply_config()` on (a) worker SSH `sshOk=False`,
  (b) worker SSH nominally OK but RESTCONF verify shows config not on
  device.
- `worker/netconsole_worker/ssh_client.py` — `run_ssh_commands_session`
  returns `sshOk=False` when all outputs are empty (catches broken pipe).
- `backend/src/services/labSsh.ts` — `runIosxeSshApply()` opens ssh2 shell,
  sends `terminal length 0` + `configure terminal` + batched config +
  `end`, parses output by matching echoed command lines.
- `backend/src/routes/interfaces.ts` — `POST /:deviceId/apply-ssh`.

**Caveats discovered:**
- The lab device rejects `vlan X / name FOO` (the Access template's body)
  with `% Invalid input detected at '^' marker.` — likely because the lab
  device only supports VLAN changes via `vlan database` (IOS 12.x style),
  not via `configure terminal` mode (which is IOS 15.x+). This is a lab
  device config issue, not a NetConsole bug. Real production IOS-XE boxes
  accept both. The pipeline correctly reports the rejection via the
  `outputs[].error` array.
- `commandCount` in the worker's job result is `None` — minor: worker
  doesn't propagate `commandCount` from the backend response into its
  result dict. Job still shows success with `outputs[]` so the operator
  sees what happened. Not blocking.
