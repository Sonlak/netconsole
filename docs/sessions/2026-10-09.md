## 09:01 – Plan: AI Assistant (LLM-powered) — full architecture

User wants a full LLM-powered AI Assistant (not v1 deterministic). Scope: answer any
question about NetConsole data AND perform actions (config push, shut/no-shut, etc.)
through natural language.

### Architecture decision: Tool-calling (not SQL generation)

**Rejected approaches:**
- LLM generates Prisma/SQL directly → hallucination risk: wrong table names, wrong joins
- LLM returns free-text from its training data → stale/wrong info about live system

**Chosen approach: Function calling (OpenAI tool_use / Claude tools)**
- Backend exposes structured TOOLS (the same functions already in the routes/services)
- LLM receives the full tool schema (name, description, parameters)
- LLM decides which tools to call based on user intent
- Each tool validates input, enforces RBAC, returns structured JSON
- LLM synthesizes a natural-language response from the tool outputs
- Every action is logged in AuditLog

This is how production AI assistants work: Copilot, Marvis, Claude for Enterprise,
Gemini in Gmail — tool-calling, not SQL generation.

### LLM Provider decision (to confirm with user)

| Option | Provider | Model | Pros | Cons |
|--------|----------|-------|------|------|
| **A (Recommended)** | OpenAI | GPT-4.1 / GPT-4.1-mini | Reliable, cheap ($0.001/1K tokens), best tool-calling | Data goes to OpenAI |
| B | Anthropic Claude | Claude 3.5 Sonnet | Excellent reasoning, great tools | ~3× cost of GPT-4.1 |
| C | Azure OpenAI | GPT-4.1 | Same as A + enterprise data residency | Requires Azure subscription |
| D | Ollama (local) | Qwen 2.5 / Llama 3.3 | Full data privacy, no API cost | Needs GPU on VPS, slower, lower quality |
| E | Groq | Llama 3.3 70B | Fast inference, open models | Requires GPU, limited tool-calling |

For a bank internal network: **Option A (OpenAI)** is simplest. The query
文本 goes to OpenAI's servers — same as every SaaS product. If user wants
full on-prem, Option D (Ollama) is the fallback but needs a GPU on the VPS.

### Implementation plan

- `backend/src/routes/assistant.ts` — `POST /api/assistant`

## 09:48 – Build: NetConsole AI Assistant (gpt-4.1-mini + prompt caching)

### What landed

**Backend** (`backend/src/services/assistant/` + `backend/src/routes/assistant.ts`):
- 12 tools split into READ (9) and WRITE (3). RBAC-gated: VIEWER gets READ only, OPERATOR+ADMIN can run WRITE.
- `prompts.ts` – system prompt (Vietnamese) + OpenAI tool catalog. Stable, sent first on every turn so prompt caching kicks in (50% off cached input → ~$1.5/dev/month at 30 q/day).
- `handlers.ts` – implementations: lookup_mac, get_device, get_device_interfaces, list_dhcp_leases, get_dhcp_pool_status, get_fabric_topology, search_recent_jobs, get_recent_logs, get_unacknowledged_alerts, queue_interface_action, queue_log_collect, queue_managed_check.
- `llmClient.ts` – thin OpenAI SDK wrapper with hard-coded pricing (micro-USD/1M tokens) for gpt-4.1-mini / 4.1 / 4o-mini.
- `persistence.ts` – AssistantSession / AssistantMessage / AssistantUsageLog CRUD.
- `assistant.ts` route – single POST /api/assistant, SSE stream (`event: message` + `data: {type, ...}` JSON). Frontend owns the conversation; backend persists audit + usage. WRITE tools emit `confirmation_required` and stop; user clicks Confirm → frontend re-POSTs with `confirmedToolCall` → backend executes + streams follow-up.

**Schema** (`backend/prisma/schema.prisma`):
- `AssistantSession` (user-scoped, has model + title)
- `AssistantMessage` (role + content + toolCalls + toolCallId, per-turn audit row)
- `AssistantUsageLog` (inputTokens + cachedInputTokens + outputTokens + costMicrodollars + latencyMs, append-only)

**Frontend** (`frontend/src/components/assistant/`):
- `api/assistant.ts` – SSE consumer with 401→refresh→retry, parses the event stream block-by-block.
- `AssistantDrawer.tsx` – right-side Drawer with sessionStorage persistence, suggested prompts, Enter-to-send, usage footer (admin only: tokens + USD).
- `MessageBubble.tsx` – user/assistant/system bubbles, tool call pills (color-coded by READ vs WRITE), inline confirmation cards.
- `ConfirmationCard.tsx` – orange-bordered card with [Xác nhận] / [Huỷ] buttons + raw args expandable.
- `MarkdownText.tsx` – hand-rolled markdown (headings/lists/code/tables/inline) — no `react-markdown` dep (~80KB saved).
- Wired into `AppLayout.tsx` header bar (RobotOutlined button, blue badge dot).

**Wiring**:
- `backend/.env.example` + `docker-compose.app.yml` get `OPENAI_API_KEY` (with `${OPENAI_API_KEY:-}` default so the assistant is disabled rather than crashing if the secret isn't set).
- `deploy.yml` writes the OPENAI_API_KEY secret to `$DEPLOY_DIR/.env` and passes it via `--env-file`. Deploy step won't fail if the secret is missing.
- `openai` package added to backend dependencies (`npm install openai`).

## 10:02 – Deploy to production + live test + 2 bug fixes

User approved deploy. Pushed commit `b66a27d` to main; CI #557 + Deploy #544 ran. Discovered `OPENAI_API_KEY` was not actually set in GitHub secrets despite earlier confirmation, so the first deploy returned "OPENAI_API_KEY is not set" in the UI. ### Bug fix #1 — OpenAI 400 in tool-result recursion

`callAndStream` skipped the assistant message when `response.text` was null but still appended the tool result. OpenAI requires every `tool` message to immediately follow an `assistant` message carrying `tool_calls`. Fix in `backend/src/routes/assistant.ts::callAndStream`: always append the assistant turn (text can be null), then the tool result. Added regression test that asserts the recursive call's messages array contains `assistant(tool_calls)` BEFORE the `tool` row.

### Bug fix #2 — multi-tool fan-out

Live test "LAB-F6-DS-01 status và interfaces" revealed the LLM was emitting 2 tool_calls in one turn (`get_device` + `get_device_interfaces`). The old `for` loop recursed after the FIRST readonly tool, so the second tool_call_id had no matching `tool` message → OpenAI 400 ("The following tool_call_ids did not have response messages: call_xxx"). Refactored the loop: collect ALL readonly tool results, then recurse once with the full set. WRITE tools still short-circuit. Added test "handles multiple tool_calls in one LLM turn (fan-out)" asserting 2 tool_result events + 2 tool messages in the recursive LLM call.

### Frontend improvement

`AssistantDrawer.sendMessage` was dropping `tool_calls` and `tool` rows from the wire when re-sending conversation history → LLM re-ran the same tool on every follow-up turn. Updated the wire builder to preserve `tool_calls` on assistant messages and emit `tool` role messages with the cached result.

### Bug fix #3 — WRITE flow prompt

The system prompt had a step "Khi user nói ok / đồng ý → tool chạy" that the LLM interpreted as "ask user first, then call the tool". LLM was returning "Bạn có đồng ý để tôi tiến hành?" as plain text, so the confirmation card never appeared. Rewrote the WRITE section to explicitly say:
- Call the tool IMMEDIATELY, do not ask in text first
- Backend auto-creates the confirmation card
- Added wrong-vs-right example to lock the behaviour
