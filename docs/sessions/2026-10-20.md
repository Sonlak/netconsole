## 10:30 – Fix dứt điểm: legitimate user bị khoá "Too many login attempts"

### Ngữ cảnh
User `sonnx` bị khóa "Too many login attempts, please try again after 15 minutes" sau khi
nhiều lần vào dashboard. Không phải do nhập sai pass nhiều lần — user chỉ nhập đúng 1 lần.
Root cause nằm ở in-memory `authRateLimit` (backend/src/middleware/rateLimit.ts).

### Nguyên nhân
- `app.use('/api/auth', authRateLimit, authRouter)` ở `index.ts:319` apply rate limiter
  vào TOÀN BỘ `/api/auth/*` (kể cả `/me`, `/refresh`, `/logout`).
- In-memory rate limit đếm CẢ LOGIN THÀNH CÔNG (200 OK cũng +1).
- Key generator lấy `req.body.username`, user `sonnx` → mọi login của user này cùng bucket.
- Max 10 / 15 min → sau 7–10 lần login (dù thành công) → 429.

Vì sao login nhiều lần? Frontend `useAuth` hook ở
`frontend/src/hooks/useAuth.ts:80-100`: khi `getCurrentUser()` fail → `clearAllAuth()` →
redirect /login → user nhập pass lại. Lặp lại nhiều lần trong session ngắn (15 min
access JWT, refresh token đôi lúc fail vì network blip / multi-tab race) → đủ 10 lần
trong 15 phút → khoá.

DB lockout ở `loginAttempt.ts` vẫn ok — chỉ tính failed attempts, không tính success.

### Thay đổi
1. `backend/src/middleware/rateLimit.ts`:
   - Thêm option `failuresOnly` cho `rateLimit()`. Khi true, response 2xx/3xx sẽ
     `res.on('finish')` decrement count → login thành công không tiêu budget.
   - Đổi `authRateLimit` sang `failuresOnly: true`, max 30 (tăng từ 10).
   - Key generator đổi prefix `login:user:` / `login:ip:` để không lẫn với các
     middleware khác.
2. `backend/src/index.ts:319`: bỏ `authRateLimit` khỏi global
   `app.use('/api/auth', ...)`. Comment giải thích lý do.
3. `backend/src/routes/auth.ts`:
   - Import `authRateLimit`.
   - Apply inline cho `POST /login` và `POST /mfa/verify` (HAI endpoint duy nhất
     cần credential-challenge gate).
   - Các endpoint khác (`/me`, `/refresh`, `/logout`, `/logout-all`, `/register`,
     `/users/*`, `/password`) chạy không rate-limit ngoài `authMiddleware` —
     như cũ trước khi có H11 hardening.

### Notes

### 15:30 -- Forced password change: rewrite to AWS IAM-style re-auth flow (commit ff430d2)

**Problem with the old implementation**:
1. `ProtectedRoute` redirected an ALREADY-authenticated user to a separate
   `/change-password-required` route. After the change it called
   `refreshUser()` + `navigate('/')` -- the user kept the access token minted
   under the OLD password and walked straight into the dashboard.
2. `PUT /api/auth/password` revoked RefreshToken rows but left the 15-minute
   ACCESS token valid. Anyone holding that token (XSS, proxy log, shoulder-surf)
   kept full API access after rotation.

**Industry standard** (AWS IAM docs.aws.amazon.com/IAM/latest/UserGuide/
id_credentials_passwords_admin-change-user.html): "Require password change at the
next sign-in" + "Revoke active console sessions" -- token is killed, user signs
in again with new password.

**Backend changes** (commit ff430d2):
- `User.passwordChangedAt` (nullable DateTime) added to schema. Prisma `db push
  --accept-data-loss` applied on deploy.
- `authMiddleware` is now async and rejects any access token whose `iat`
  predates `passwordChangedAt` (1s clock slack). Cached in-process for 30s
  and dropped synchronously on rotation via `invalidatePasswordCache()`.
  This is the `DateLessThan: aws:TokenIssueTime` equivalent.
- `PUT /api/auth/password`: sets `passwordChangedAt = now()`, calls
  `invalidatePasswordCache()`. Admin reset deliberately does NOT stamp
  `passwordChangedAt` (the target must still log in with the new password
  to reach the change form).
- WebSocket terminal uses the HttpOnly refresh cookie (already revoked on
  rotation) -- no change needed.

**Frontend changes**:
- `LoginPage` is now a 3-stage machine: credentials / MFA / change-password.
  Change-password stage shown BEFORE dashboard is reachable.
- After successful change: `logout()` clears local state, success banner
  "Password updated successfully. Sign in with your new password.", username
  pre-filled.
- Deleted `ChangePasswordRequiredPage.tsx` + its route.
- `ProtectedRoute` no longer special-cases `mustChangePassword`.

**E2E test result** (on production):
  - Login with OLD password -> mustChangePassword=true ✅
  - Pre-rotation token baseline works (200) ✅
  - Password rotated -> pre-rotation token -> **401 "Session invalidated by password change"** ✅
  - New password works, old password rejected ✅
  - mustChangePassword cleared after rotation ✅

Deploy: CI #39393471838, success.

### 16:17 — MFA OTP stage left user stranded on login form (commit 8c9245b)

**Bug report**: After entering valid TOTP code, the page jumped back to the
login form instead of NetConsole dashboard. A manual reload fixed it.

**Root cause**: LoginPage stored `stage` in `useState` and updated it from a
`useEffect` keyed on `(pendingMfa, user?.mustChangePassword, stage)`. After a
successful OTP verify:
- `pendingMfa` → null (cleared by `verifyMfaCode`)
- `isAuthenticated` → true
- `stage` stayed `'mfa'` because no branch of the effect matched — the first
  arm required `pendingMfa` (now null), the second required `mustChangePassword`
  (false), and the third required `stage !== 'mfa'` (false).

The redirect effect was gated on `stage === 'credentials'`, so it never fired.
The render fell through `stage === 'mfa' && pendingMfa` (pendingMfa null) back
to the credentials form. A reload appeared to fix it only because `hydrate()`
reads the token back out of localStorage.

**Fix**: derive `stage` from auth state instead of storing it:

```
pendingMfa                 → 'mfa'
isAuthenticated + mustChange → 'change-password'
otherwise                   → 'credentials'
```

No second copy exists to drift. Post-OTP, `stage` collapses to 'credentials',
the redirect fires, and the user lands in NetConsole. The same derivation
restores the login form after `handlePasswordChangeDone` and after "Back to
login" from MFA without any manual reset.

**Verified**:
- E2E OTP flow on production: login → TOTP → 200 session token → protected
  endpoints accept it ✅ (no reload needed)
