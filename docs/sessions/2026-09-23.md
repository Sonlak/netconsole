## 08:28 — fix(managed-check): audit + 4 performance fixes (deploy #431)

**User:** "coi lại doc, các file md thử. phần managed check đang hoạt động như thế nào? tôi thấy mỗi lần bấm managed check thao tác rất lâu, các trạng thái status ping, ssh, rest/netconf thì rest/netconf hiện xanh lên cũng lâu, lúc device bị offline, online trở lại. rà soát lại cho tao thử nhé"

**Audit findings:**

| Symptom | Root cause |
|---------|-----------|
| Click "Managed check" takes 30-65s | Juniper `probe_identity` had 3-hop chain: NETCONF (20s) + RESTCONF (30s) + CLI (15s) = 65s worst case. cRPD on containerlab returns OpenSSH banner at port 830 (no real NETCONF subsystem), so NETCONF always failed → full chain ran |
| REST/NETCONF flag stays red after device comes back online | `MANAGED_CHECK_INTERVAL_SECONDS=600` (10 min). Ping detect ONLINE instantly, but REST flag only updated by scheduler tick up to 10 min later |
| Watchdog kills legitimate Juniper jobs | `MANAGED_CHECK` stale threshold was 120s, but Juniper chain could legitimately take 65s, leaving only 55s margin |
| Frontend shows "Job wait timeout" for jobs still making progress | `waitForJob` timeout was 45s, but Juniper uptime chain + watchdog allowance = 240s for Juniper. UI gave up before worker finished |

**Fixes applied (commit `1124b81`):**

### Fix 1 — Auto-trigger MANAGED_CHECK on ping recover
File: `backend/src/services/devicePing.ts`

Added a recover hook in `pingAndUpdateDevice`: when a device transitions
`OFFLINE/UNKNOWN → ONLINE`, the function now calls `tryCreateDeviceJob`
to enqueue an urgent `MANAGED_CHECK` job immediately. The job runs
within ~1s of the ping recovery (next worker poll), rather than waiting
up to 10 min for the scheduler.

```typescript
if (
  ping.alive &&
  (previousStatus === DeviceStatus.OFFLINE || previousStatus === DeviceStatus.UNKNOWN) &&
  nextStatus === DeviceStatus.ONLINE
) {
  const outcome = await prisma.$transaction(async (tx) =>
    tryCreateDeviceJob(tx, device.id, JobType.MANAGED_CHECK, null),
  );
  // logs: `[ping] FOO recovered OFFLINE→ONLINE, queued MANAGED_CHECK <id>`
}
```

### Fix 2 — Shorten Juniper uptime chain to single-transport
File: `worker/backends/juniper.py::probe_identity`

Previous chain was:

```
NETCONF SSH (20s) → RESTCONF (30s) → CLI SSH (15s)
```

New logic: pick ONE best transport based on which port is already known to
be open from the TCP probe phase, try it once with a 5s timeout. If it
fails, skip uptime rather than chaining.

```python
uptime_timeout_s = 5.0
if self.config.junos_netconf_ssh and netconf_open:
    uptime = nc_fetch_system_uptime(..., timeout=uptime_timeout_s)
    if uptime["ok"]:
        parsed.update(...)
        uptime_fetched = True
# ... RESTCONF (5s) ... CLI (5s)
if not uptime_fetched and api_open:
    message = message + " (uptime fetch skipped: no responsive transport)"
```

Worst case: ~5s instead of ~65s.

### Fix 3 — Increase watchdog for MANAGED_CHECK
File: `backend/src/services/jobWatchdog.ts`

- Baseline: 120s → 180s
- Juniper extra: +60s (total 240s for Juniper)

Covers the (now-rare) cold SSH session spike even after the chain refactor.

### Fix 4 — Reduce scheduler interval
File: `docker-compose.app.yml`

`MANAGED_CHECK_INTERVAL_SECONDS: 600 → 180` (3 min instead of 10 min).
Previous interval was tuned for a heavy SSH-based probe; the TCP-only probe
is ~2-5s per device, so 3 min is fine. Safety net in addition to Fix 1.

### Fix 5 — Increase frontend wait timeout
File: `frontend/src/pages/DeviceDetailPage.tsx::handleCheckManaged`

`waitForJob` timeout: 45s → 90s. On timeout, the page now refreshes from
the last persisted device row and shows a `message.warning` with "showing
latest state" instead of erroring out.
