## 22:50 — Deploy pipeline hardening: 3 fixes to recover from cascade failure

### What broke

Today's deploy of `3adfd01` (phase 1+2: zero-downtime, worker scale, redis cache) failed in CI step "Build & restart app services" and stayed failed across two retries. Site was running but CI was red; auto-rollback also failed. User asked: "lỗi code hay do cách deploy?"

### Root cause: 3 stacked bugs (all in `3adfd01`'s compose changes)

**Bug 1 — IP conflict** (`docker-compose.app.yml` redis svc)
- New `redis` service at `172.31.0.21` collided with `netbox-redis` (from `docker-compose.netbox.yml`) at the same IP.
- Symptom: `netconsole-redis` container stuck in "Created" with `err: failed to set up container networking: Address already in use`.
- Fix: `c1981ee8` — moved redis to `172.31.0.23` (free). Updated `REDIS_URL` env.

**Bug 2 — broken container not cleaned up** (`.github/workflows/deploy.yml`)
- `Build & restart` step's `stop/rm` only handled `backend worker frontend`; the broken redis container from a previous failed deploy persisted into the next run.
- Symptom: even after Bug 1's IP fix, the next deploy's `up -d` couldn't create a healthy redis (compose saw the broken container with old IP .21). Cascade: redis dead → backend unhealthy → workers never start (depends_on: backend: service_healthy) → `up -d` returns non-zero.
- Fix: `db817aa` — added `redis` to `DEPLOY_SERVICES` so all 4 ops (stop/rm/pull/up) include it.

**Bug 3 — healthcheck uses missing `curl`** (`docker-compose.app.yml` backend healthcheck)
- Phase 1 healthcheck `["CMD-SHELL", "curl -sf ... /api/health"]` always fails: `node:22-bookworm-slim` image doesn't install curl. `FailingStreak: 23`, `health: unhealthy`.
- Cascade: backend `Up (unhealthy)` → workers depends_on: backend: service_healthy never resolves → workers stay in "Created" state.
- Fix: `df7ac1f` — replaced `curl` with Node one-liner using `require('http').get(...)`. No Dockerfile change, no image rebuild.

### Recovery actions (manual, on VPS — non-ideal but unblocks live traffic)

After each failed deploy I had to manually recover the workers because `up -d` would not start them. The pattern was always the same:
1. `docker rm -f netconsole-redis` (force-remove the broken "Created" container)
2. `docker compose up -d redis` (recreate with the fixed config)
3. `docker start netconsole-worker-1 netconsole-worker-2` (manually start workers since up -d gave up)
4. Markers `.last-deploy-sha`/`.rollback-before-deploy-sha` are missing because rsync --delete wiped them; auto-rollback is broken until those are restored

### What I learned (add to gotchas #5)

- **`docker compose up -d X Y` does NOT prevent creation of OTHER services in the project** — `--no-deps` only ignores `depends_on`, not "create missing services". If a sibling service has a different config, it will be reconciled. List ALL services in the project explicitly in `DEPLOY_SERVICES` to avoid partial-update traps.
- **The backend image is `node:22-bookworm-slim` with no curl/wget/nc** — only `iputils-ping, openssl, ca-certificates, postgresql-client`. Any healthcheck or init script that uses `curl` or `wget` will silently fail with "command not found" in FailingStreak. Use Node's `http`/`https` module for HTTP probes, or extend the Dockerfile (extra 5-10 MB image cost).
- **`set -euo pipefail` + a hung `docker compose up -d` = silent timeout** — the `up -d` command returns non-zero only AFTER timing out, not when the cascade actually starts. Deploys hang for 2+ min before failing. With `--no-deps --wait` (or explicit `docker start` per replica) the failure mode is faster and more obvious.
