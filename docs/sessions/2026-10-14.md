# 2026-10-14

## 08:30 — Phase 1 + 2 implementation (zero-downtime deploy + worker scale-out + cache)

### What changed

**Phase 1 — Zero-downtime deploy**

- **`worker/netconsole_worker/main.py`** — added SIGTERM/SIGINT handlers + 300s drain phase. In-flight Juniper writes (worst case ~120s) finish cleanly; watchdog reclaims anything beyond DRAIN_TIMEOUT_SECS=180s.
- **`docker-compose.app.yml`** — backend got `healthcheck: curl /api/health` + `stop_grace_period: 30s`. Worker got `stop_grace_period: 300s` to allow drain. Backend already had graceful shutdown in `index.ts` (unchanged).

**Phase 2 — Worker horizontal scale + atomic claim**

- **`backend/prisma/schema.prisma`** — added `Job.startedAt DateTime?` + `Job.claimedBy String?` for claim audit. Additive, nullable — no backfill.
- **`backend/src/routes/jobs.ts`** — `/jobs/queue` now atomically claims via `SELECT … FOR UPDATE SKIP LOCKED` inside a transaction. Multiple worker replicas get disjoint job sets with zero wasted polls.
- **`worker/netconsole_worker/main.py`** — `run_job` no longer calls `PATCH /jobs/{id}/claim` (queue now claims atomically). Worker passes `?workName=` so the backend stamps `Job.claimedBy` for debugging.
- **`backend/src/services/jobWatchdog.ts`** — uses `COALESCE(startedAt, updatedAt)` so existing RUNNING rows keep working until they get re-claimed.
- **`docker-compose.app.yml`** — worker `replicas: 2`. Removed `container_name` + `ipv4_address` (compose auto-names `netconsole-worker-1/-2` and auto-IPs them). Backend stays `replicas: 1` for now — true zero-downtime needs an LB in front (Phase 3 / multi-node work).

**Phase 2 — Hot-read cache**

- **`backend/src/lib/redis.ts`** (NEW) — ioredis singleton, lazy-connect, offline-queue disabled (fail fast, fallback to PG).
- **`backend/src/services/deviceCache.ts`** (NEW) — read-through cache for `/api/devices`. 30s TTL, JSON-encoded, invalidates on POST/PATCH/PUT/DELETE /devices. Field-level updates (ping, managed check) intentionally don't invalidate — TTL is the freshness guarantee.
- **`backend/src/routes/devices.ts`** — `GET /` wraps `prisma.device.findMany` in `deviceCache.getDevicesList()`. POST/PATCH/PUT/DELETE call `deviceCache.invalidate()`.
- **`docker-compose.app.yml`** — added `redis` service at `172.31.0.21`, `maxmemory 256mb allkeys-lru`, no persistence (cache rebuilds on next request).
- **`backend/package.json`** — added `ioredis@^5.4.2`.

### What's next (backlog)

- **PgBouncer** — skipped at current scale (1 backend × Prisma's `connection_limit=10` is fine under PG's 100 max_connections). Re-evaluate when total app clients > 50; track via `SELECT count(*) FROM pg_stat_activity`.
- **Backend `replicas: 2` + LB** — true zero-downtime (currently ~1-2s window from graceful shutdown alone). Needs a tiny `nginx` or `traefik` sidecar in front of backend, plus frontend `proxy_pass` update.
- **Phase 3 (multi-node)** — when this VPS hits ~70% CPU/RAM sustained. Defer until the new VPS is provisioned.

### Known risks / things to watch on first deploy

1. **`prisma db push --accept-data-loss` at backend boot** — the two new columns are nullable + additive so `--accept-data-loss` shouldn't actually drop anything, but the flag stays for safety per the existing deploy.yml contract.
2. **Worker `replicas: 2`** — first deploy after this change removes the old `netconsole-worker` (container_name=netconsole-worker) and creates `netconsole-worker-1/-2`. Existing deployments have a 30s window where there are zero workers. Acceptable — the backend's watchdog reclaims any in-flight RUNNING jobs that get orphaned.
3. **Redis** — if Redis fails to start, backend's healthcheck never goes green (Redis is in `depends_on`). Compose rolling update won't proceed. Boot logs in `docker logs netconsole-redis` for the diagnosis.
