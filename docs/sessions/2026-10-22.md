### 02:05 -- Deploy Dev chạy xanh sau khi sửa 3 lỗi trong workflow

**Bối cảnh:** test deploy qua `vps-dev-01` (old VPS, Tailscale `100.102.133.86`). Deploy fail liên tục 6 lần, mỗi lần ~2-3 phút.

**Ba lỗi đã sửa (cùng một nhóm nguyên nhân):**

1. **Health check probe sai địa chỉ.** Cả 3 workflow probe `http://172.31.0.3:3000/api/health` (container IP). Host → docker-bridge bị chặn bởi `FORWARD policy DROP` + rule Tailscale `ts-forward`, nên probe luôn timeout dù container healthy. Đổi sang `127.0.0.1:3000` (published port — cũng đúng đường đi thật của client). Timeout 90s → 120s để hấp thụ image pull từ GHCR.

2. **rsync `--delete` không exclude `node_modules/`.** `/opt/netconsole/backend/node_modules` là root-owned 328M / 7493 file từ một lần build trực tiếp trên VPS cũ. Mỗi deploy rsync cố unlink từng file → hàng nghìn dòng `Permission denied (13)` làm nghẽn log và ăn hết time budget trước khi tới bước compose. Thêm `node_modules/`, `.venv/`, `__pycache__/` vào exclude của cả 3 workflow. (Dockerfile tự chạy `npm ci` trong build stage nên bản copy trên VPS vô dụng — đã xoá.)

3. **Thiết kế sai khiến lỗi nhỏ thành outage toàn bộ.** Workflow chạy `stop` + `rm -sf` **trước**, rồi mới `up -d`. Nếu `up` fail bất kỳ lý do gì, toàn bộ app stack bị xoá sạch; health check chỉ biết "không kết nối" và **mất luôn lỗi gốc của compose**. Thay bằng `up -d --force-recreate --remove-orphans` — container cũ giữ nguyên cho tới khi container mới tạo xong. Bỏ `--no-deps` để compose chờ đúng thứ tự health (postgres → redis → backend → frontend/worker). `up` fail giờ là hard fail kèm dump state, thay vì bị nuốt bởi fallback "sweep Created containers" (fallback này không bao giờ tìm thấy gì vì container đã bị `rm`).

**Thêm diagnostics:** health check fail giờ in ra container list, backend state + exit code + restart count, 60 dòng backend log, và các port đang listen. Không còn trường hợp "biết fail mà không biết vì sao".

**Kết quả:** `Deploy Dev` #39708928152 **success** (4m36s), `CI` #39708928153 **success**. Trên VPS: backend 200, frontend 200, 7 container up/healthy, image đã ghim theo commit SHA `4689aa5`.

**Bài học:**
- Không bao giờ `rm -sf` container trước khi đã xác nhận thay thế tạo được. Giữ container cũ làm lưới an toàn.
- Fallback kiểu `|| { sweep }` chỉ có hại: nó biến lỗi thật thành im lặng.
- Health check phải probe published port, không probe container IP — đường đi đó phụ thuộc firewall và không phản ánh trải nghiệm client thật.

### 11:20 -- Prod: dọn blocker trước lần deploy đầu tiên

**Câu hỏi của user:** "prod đã có sẵn môi trường chưa, pull code về chạy thôi đúng không?" → **Không.** Prod (`netconsole-pd`, `192.168.81.171` LAN / `10.10.20.40` lab) trống hoàn toàn: 0 container, chưa từng deploy, không marker file, không `/opt/netconsole`. Ngoài ra có 4 blocker mà nếu không sửa thì lần deploy đầu chắc chắn đỏ.

**Blocker 1 — `/opt` không writable, step đầu tiên của workflow fail.**
Runner chạy với user `sonnx`, nhưng `/opt` thuộc `root` (755). Step "Save rollback marker" làm `mkdir -p /opt/netconsole` → `Permission denied` → fail ngay bước đầu. Đã bootstrap `/opt/netconsole` thuộc `sonnx` (đúng pattern của VPS cũ: `/opt` root, `/opt/netconsole` sonnx).

**Blocker 2 — compose publish port trên IP của VPS CŨ.**
`docker-compose.app.yml` publish kea DHCP `:67`, kea ctrl-agent `:8001` và backend syslog `:1514` trên host IP `10.10.20.20` — đó là lab IP của **VPS cũ**, không có trên prod. Test thật trên prod: `failed to bind host port 10.10.20.20:67/udp: cannot assign requested address` (rc=125), còn `10.10.20.40` thì OK (rc=0). Hệ quả: `kea-dc1` không start → `backend` (`depends_on: kea-dc1: service_healthy`) không start → deploy fail ở step "Wait for backend healthy".

Fix: tham số hoá IP trong file gốc — `${KEA_HOST_IP:-10.10.20.20}` cho 3 port binding, `${KEA_SERVER_URL:-10.10.20.20}` cho kea HA. `deploy-prod.yml` ghi `KEA_HOST_IP=10.10.20.40` + `KEA_SERVER_URL=10.10.20.40` vào `/opt/netconsole/.env`. Đã verify `docker compose config` trên prod: prod ra `10.10.20.40`, dev (không set biến) vẫn ra `10.10.20.20` — hành vi dev không đổi.

**Bài học:** override `ports` trong file overlay **không** thay được list gốc — compose vẫn append nên binding `10.10.20.20` còn nguyên. Phải sửa ở file gốc, không sửa ở overlay.

**Blocker 3 — auto-rollback đã chết âm thầm.**
`rollback.yml` trigger `workflow_run: workflows: ["Deploy"]`, nhưng sau khi tách dev/prod (commit `0e4658e`) workflow tên là **"Deploy Dev"** và **"Deploy Prod"** — không còn workflow nào tên "Deploy" → trigger khớp 0 cái, không hề báo lỗi. Sửa thành `["Deploy Prod"]` (rollback chạy trên `vps-prod-01`, `DEPLOY_DIR=/opt/netconsole` → chỉ được phản ứng với prod deploy). Thêm guard **fresh host**: host chưa từng có deploy thành công thì skip hẳn, **không** rơi vào `FALLBACK_SHA` (`2113812` — commit cũ), vì deploy commit cũ lên host mới tệ hơn là để nguyên deploy fail cho người xem. 6 step sau được chặn bằng `if: steps.marker.outputs.SKIP_ROLLBACK != 'true'`.

**Blocker 4 — secret không còn là blocker nữa.**
Không cần user paste `SOPS_AGE_KEY` vào GitHub: `deploy-prod.yml` đã hỗ trợ fallback `SOPS_AGE_KEY_FILE=/opt/netconsole/.sops-age-key.txt`. Đã đặt age key (chmod 600) ở đó và verify decrypt `secrets.env.enc` ngay trên prod: OK, đủ **17** biến mà compose yêu cầu (`:?`). Ngoài ra GHCR package là **public** → VPS không cần `docker login`.

**Vệ sinh:**
- `.gitignore` thêm `/secrets.age.key` — private key của age đang untracked mà **không** ignored, chỉ cách `git add -A` một bước là lên GitHub.
- Thêm `secrets.age.key` vào rsync exclude của cả 3 workflow.
- VPS cũ **không bị đụng**: 7 container vẫn up/healthy. Đã xoá age key + file tạm khỏi `/tmp` của nó.

**Blocker 5 — build image kea fail trên prod (phát hiện khi chạy CI thật).**
Deploy đầu tiên fail ở step "Build & restart": `E: Unable to locate package kea-dhcp4-server`, `E: Package 'ca-certificates' has no installation candidate` — tức `apt-get update` không lấy được package index nào.

Root cause (test từng bước trên prod):
- Prod **không có egress internet trực tiếp**: `curl --noproxy '*'` tới `deb.debian.org` / `archive.ubuntu.com` đều timeout ở cả HTTP lẫn HTTPS, ping 8.8.8.8 100% loss. Mọi traffic ra ngoài phải đi qua proxy `192.168.154.101:1985` (khai trong `/etc/environment`, `/etc/profile.d/proxy.sh`, và `Environment=` của systemd runner service).
- Docker **không** tự đẩy proxy env của client vào `docker build`: build có `http_proxy` trong env → vẫn fail; build với `--build-arg HTTP_PROXY=... --build-arg HTTPS_PROXY=...` → **thành công**.
- Vì sao backend/worker/frontend vẫn build được: chúng do job `push-images` build trên `ubuntu-latest` (GitHub-hosted, internet đầy đủ). Chỉ `kea-dc1` có `build:` trong compose nên bị build **tại chỗ trên VPS** → fail.

Fix: đưa kea vào job `push-images` (matrix thêm `service: kea`, context `lab/kea`) và override `kea-dc1` trong `docker-compose.app.prod.yml` bằng `image: ghcr.io/sonlak/netconsole-kea:${GITHUB_SHA:-main}` + `pull_policy: always`; thêm `kea-dc1` vào `DEPLOY_SERVICES`. Dev VPS không đổi (vẫn build kea local qua base compose, có internet).

Đã verify trên prod rằng Compose với `build:` + `image:` + `pull_policy: always` sẽ **PULL** image từ GHCR chứ không build local (test bằng Dockerfile cố tình `exit 1` + image `netconsole-frontend:main` → pull thành công, container chạy).

**Còn lại:**
- Merge `test/dev-deploy-flow` → `main` (fast-forward được, `origin/main` là ancestor) → CI chạy `Deploy Prod` trên `vps-prod-01`. `deploy-dev.yml` đã `branches-ignore: main` nên push `main` không đụng VPS cũ.
- Sau khi CI push image `netconsole-kea` lên GHCR, cần kiểm tra package đó có **public** không (các image cũ đều public) — nếu private thì prod pull sẽ bị `denied` và cần user đổi visibility.
- **Cần user quyết:** prod và VPS cũ cùng nằm trên segment `10.10.20.0/24` và cùng là `primary` với peer `kea-dr1` (`10.10.20.30`). Khi cả hai cùng chạy kea, DR nhận 2 lời "tôi là primary" → trạng thái HA của DR mơ hồ. Ngày đầu chưa client nào trỏ `10.10.20.40:67` nên vô hại, nhưng cần chốt lịch cắt (dừng kea trên VPS cũ / sửa switch DHCP helper-address) khi cut-over.
- Entry point public cho prod vẫn chưa có — user truy cập qua `192.168.81.171:8443`.
