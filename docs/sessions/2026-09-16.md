**Conclusion:** IOSv 15.2 lightweight image just doesn't ship the
NETCONF/RESTCONF subsystem. `netconf-yang` and `netconf ssh` are accepted
in config but the daemon doesn't start. SSH KEX is `group1-sha1` which
paramiko 3.x dropped — only the system `ssh` CLI with explicit
`KexAlgorithms=+diffie-hellman-group1-sha1` works.

**Architecture chosen: hybrid**

- **READ** (interfaces/ARP/MAC/LLDP/config/show-run) → **IOSexec HTTP**
  (port 443, TLS 1.0, Basic auth, CSRF token)
- **WRITE** (apply_config/interface_action/rollback) → **SSH via
  sshpass + OpenSSH CLI with `-tt` + stdin commands** (each request is
  one interactive session that does `conf t` → commands → `end` → `exit`)

### Two non-obvious bugs hit during testing (documented in code)

1. **TLS context** — `ssl.PROTOCOL_TLS_CLIENT` defaults to TLS 1.2+ and
   IOSv rejects the handshake with `SSLV3_ALERT_HANDSHAKE_FAILURE`.
   Solution: `ssl.SSLContext(ssl.PROTOCOL_TLSv1)` + `@SECLEVEL=0` ciphers.
2. **Form data** — POST to `/level/15/exec/-` MUST include `command_url`
   in the body, not just `command`. Without it, server sends the request
   to `/-/CR` and silently discards everything.
3. **HTTP writes** — `configure terminal\n<cmd>\nend` via `conf=1`
   form-data DOES NOT WORK. Server splits the form-data command on `/`
   for the URL-display path but the actual command sent to IOS ends up
   with extra `/` separators that break `end`. Documented as "HTTP
   multi-command configure broken; SSH fallback for writes."
4. **SSH writes** — `ssh host 'cmd1; cmd2; cmd3'` (semicolons) doesn't
   work because IOS exec doesn't interpret `;`. Solved by
   `sshpass + ssh -tt` with `conf t\ncmd1\ncmd2\nend\nexit\n` piped to
   stdin.

**Problem:** After the 14:00 deploy, the IOS device (10.10.20.211) was still NOT
being managed. Investigation showed:

1. `probeIosHttpExecIdentity` in `backend/src/services/iosxeRest.ts` returns
   `vendor: 'Cisco'` for ALL Cisco devices discovered via HTTP (both plain IOS
   AND IOS-XE).
2. Worker `detect_vendor(device)` matches `vendor='Cisco'` → returns `'iosxe'`
3. `IOSxeBackend` tries RESTCONF/NETCONF which plain IOS doesn't have.
4. Managed check fails → device stays OFFLINE.

**Fix (2 files):**

`backend/src/services/iosxeRest.ts` — in `probeIosHttpExecIdentity`, detect
plain IOS vs IOS-XE by checking for `Bootstrap program is <model>` in the
`show version` output. Plain IOS always has this line; IOS-XE doesn't (IOSd
runs as a separate process). When detected as plain IOS, set
`fields.vendor = 'ios'` instead of the default `'Cisco'`.

`docker-compose.app.yml` — added to worker environment:
  `IOS_HTTP_ENABLED: "true"` + credentials so the worker routes to `IOSBackend`.

**Verification after deploy:**
- Device LAB-F3-AS-01 (10.10.20.211) gets `vendor='ios'` in DB
- Worker `select_backend(device)` → `IOSBackend` (not `IOSxeBackend`)
- Managed check succeeds, device goes ONLINE → MANAGED
